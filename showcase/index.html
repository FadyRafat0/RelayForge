    ENGINEERING DECISIONS

    Reliability comes
    from the handoffs.

    PostgreSQL owns the delivery state. Redis coordinates work. Workers send HTTP requests. Each boundary has a failure case to handle.

    →→→→→
    DURABILITY

    Why save before queueing?

    An accepted event and its delivery records commit together. If Redis is unavailable, PostgreSQL still remembers the work. The dispatcher can publish it later.

    DELIVERY SEMANTICS

    Why allow duplicates?

    A receiver can commit its effect and lose the HTTP response. The sender cannot know that it succeeded. Retrying is necessary; receiver-side idempotency makes repetition safe.

    CRASH RECOVERY

    Why claim with a lease?

    A permanent lock would strand work after a worker crash. Expiring database leases let another worker retry, while ownership tokens stop late completions overwriting newer state.

    CONCURRENCY

    Why separate Redis connections?

    A blocking stream read must not delay acknowledgements or token-bucket checks. Separate connections keep these operations independent.

    A bug found by measuring the whole path.

    The first load test found workers acknowledging jobs whose rows were still locked by the dispatcher. Waiting for the specific row fixed the handoff; a real PostgreSQL lock-wait regression test now covers it.

    MEASURED, NOT ESTIMATED

    Fast acceptance.
    Delivery has its own clock.

    A quick HTTP response means the event is saved. It does not mean the webhook has arrived. These local k6 runs measure the two separately.

    1 endpoint1 worker · concurrency 410-second workloadsDefault dispatcher: 10 jobs / cycle

    WHAT THE RESULT SHOWS

    The dispatcher sets the pace.

    At 20 events/sec, the API keeps accepting work quickly while the dispatcher’s ten-job batches create a backlog. All 200 deliveries finish, but delivery p95 rises to 9.70 seconds.

    WHAT IT DOES NOT SHOW

    This is not maximum capacity.

    These are short runs on one shared local machine with one small payload and a success-mode receiver. They do not establish steady-state capacity or a production SLO.

    Reproduce the measurement. 
    npm run benchmark -- --rate 20 --seconds 10

    Each run provisions its own Docker project, checks delivery and receiver-effect counts, exports JSON, and removes only its own temporary resources.

    RUN THE REAL SYSTEM

    One command. The full stack.

    Clone the repository, open its folder, and start Docker with Linux containers. Then run: 

    docker compose -f compose.demo.yaml up -d --build --wait

    The API is available at http://127.0.0.1:3100. This starts PostgreSQL, Redis, the API, dispatcher, worker, and signature-verifying receiver.
