# Checkpoint 1C: the PostgreSQL schema

## Relationships

```text
events (one) --------< deliveries (many) >-------- (one) webhook_endpoints
                           |
                         (one)
                           |
                         (many)
                    delivery_attempts
```

A payment event sent to two destinations produces one event row and two delivery rows. If one destination fails twice before succeeding, its delivery has three attempt rows. The original event payload is stored once.

## Tables

### webhook_endpoints: where to send

- `id`: UUID primary key, generated by PostgreSQL.
- `name`, `url`: destination label and HTTP(S) URL. The database checks only basic URL format. The endpoint API must later validate URLs and the worker must enforce outbound network restrictions.
- `event_types`: nonempty text array of subscriptions; `['*']` matches all event types. Event ingestion now creates deliveries using these subscriptions and enabled status.
- `enabled`: pause a destination without deleting its history.
- `created_at`, `updated_at`: creation and most recent update times.

Migration 004 adds the randomly generated signing secret; migration 007 adds the
per-endpoint rate limit. The API validates complete URL syntax and the worker
enforces outbound address restrictions. This is a single-project local schema;
authentication and tenant ownership are not implemented.

### events: what happened

- `id`: UUID primary key.
- `type`: event name such as `payment.succeeded`.
- `payload`: JSON object stored as `jsonb`. PostgreSQL checks that this is an object, not a string or array.
- `idempotency_key`: optional client-supplied key. A unique constraint arbitrates duplicate non-NULL keys; many events can omit it. Ingestion now returns the original event for identical retries and 409 for changed type/payload. The API uses ON CONFLICT and a fresh SELECT to handle concurrent retries safely.
- `created_at`: when the event was stored.

Events will be treated as immutable by the application. No immutability trigger or restricted database role exists yet.

### deliveries: work we owe

- `event_id`, `endpoint_id`: foreign keys requiring both referenced rows to exist.
- `UNIQUE(event_id, endpoint_id)`: one delivery obligation per event/destination pair.
- `status`: `pending`, `processing`, `succeeded`, or `dead`.
- `attempt_count`, `max_attempts`: nonnegative count and positive retry budget, initially zero and five. Count cannot exceed the budget.
- `next_attempt_at`: when pending work becomes eligible; retries will return to pending with a later time.
- `completed_at`: required for succeeded/dead deliveries, absent for unfinished work.
- `created_at`, `updated_at`: lifecycle timestamps.
- `last_enqueued_at`, `last_stream_id`: migration 002 adds queue publication markers. They remain NULL until dispatch and do not indicate successful delivery. Stale pending deliveries can be republished to recover lost Redis entries.

The dispatcher queues due pending deliveries and recovers expired worker leases. Migration 003 adds active_attempt_id, lease_owner, and lease_expires_at; processing requires all three fields. A composite foreign key keeps the active attempt tied to its own delivery. The worker commits the claim before HTTP and completes only under a valid token and unexpired lease. Migration 006 now adds audited manual replay of dead deliveries; see dead-deliveries.md.

### delivery_attempts: what happened during one send

- `delivery_id`: required foreign key to a delivery.
- `attempt_number`: positive sequence number, unique within a delivery.
- `outcome`: `in_progress`, `succeeded`, `failed`, or (since migration 003) `abandoned` for expired claims with unknown HTTP outcome.
- `http_status`: optional HTTP response code, constrained to 100–599. Network failures may have no response.
- `error_message`: optional failure detail.
- `started_at`, `finished_at`: timing; unfinished attempts have no finish time. Successful attempts require a 2xx response and no error message.

The worker must later update the attempt and its parent delivery consistently in a transaction. Constraints validate rows, but do not enforce every transition or keep attempt_count synchronized automatically.

## PostgreSQL concepts used

- **Primary key:** uniquely identifies a row and cannot be NULL.
- **Foreign key:** prevents references to missing rows. Deletion is restricted so removing an endpoint/event does not accidentally erase delivery history.
- **UNIQUE:** rejects duplicate values or value combinations.
- **CHECK / NOT NULL:** reject invalid row values and missing required data.
- **timestamptz:** stores a precise instant; display uses the session time zone.
- **Index:** speeds certain lookups at the cost of storage and write work. Primary/unique keys create indexes automatically; foreign keys do not automatically index the referencing columns.
- **Partial index:** our pending-delivery index contains only pending rows, ordered by due time and ID.
- **Trigger:** refreshes updated_at on endpoint/delivery updates. A DEFAULT alone runs only during INSERT.

Initial indexes support creation-time lists, deliveries for an endpoint, attempts for a delivery, deliveries for an event, and pending work by due time. We will evaluate query plans and tune them later; there are no benchmark claims.

## Running migrations

```sh
npm run db:up
npm run db:migrate
```

The runner reads numbered SQL files from migrations/, takes a PostgreSQL advisory lock to serialize migration commands, then checks schema_migrations. Each pending file and its history record commit in one transaction on one dedicated connection. A failed file rolls back; earlier successful files remain applied.

Run the command again: completed files are skipped. Checksums detect edits to applied SQL, and missing/out-of-order history is rejected. Add a new numbered migration to change the schema. Do not edit an applied migration. SQL files use LF line endings on Windows and Linux to keep checksums consistent.

Migrations run explicitly, not automatically when the API starts. For this checkpoint, /health still checks connectivity, not migration state. There is no down/reset command: future schema changes should be separate reviewed migrations.

## Inspecting the result

```sh
docker compose exec postgres psql -U relayforge -d relayforge
```

Inside psql:

```sql
\dt
\d deliveries
SELECT name, applied_at FROM schema_migrations;
\q
```

The first two are psql commands that list tables and describe a table. SELECT is SQL. \q exits psql.

## Tests

`npm run test:integration` verifies schema behavior against real PostgreSQL. Schema/migration suites create randomly named relayforge_test_* schemas and drop only their own schemas afterward. Existing application tables are not truncated or changed. The migration rollback fixture deliberately fails after creating a table to verify that no partial DDL survives.

References: [PostgreSQL constraints](https://www.postgresql.org/docs/18/ddl-constraints.html), [node-postgres transactions](https://node-postgres.com/features/transactions).


## Receiver-owned example data (checkpoint 4C)

Migration 005 adds receiver_receipts and receiver_effects. These belong to the receiving example application and have no foreign keys to sender tables. A composite primary key (receiver_id, delivery_id) identifies completed deliveries, and an effect row references its receipt. Both inserts commit in one transaction. See [receiver-deduplication.md](receiver-deduplication.md) for concurrency and crash behavior.


## Manual replay audit (checkpoint 4D)

Migration 006 adds delivery_replays, referencing deliveries. Each row retains a reason, previous attempt count/budget, and a bounded additional budget. A unique delivery/count key protects replay generations. Reopening the delivery and saving this audit row share one transaction. A partial index supports newest-first dead-delivery listing. See [dead-deliveries.md](dead-deliveries.md).


## Endpoint admission policy (checkpoint 5A)

Migration 007 adds rate_limit_per_second (integer, default 10, allowed 1?1000) to webhook_endpoints. PostgreSQL stores configuration and durable deferred due times; Redis holds expiring per-endpoint token state. A denied admission creates no delivery_attempts row and consumes no attempt budget. See [rate-limits.md](rate-limits.md).
